01 — Objetivo

Objetivo da entrega inicial

Demonstrar, em um único totem de bancada, o fluxo ponta-a-ponta do P.O.T.O: acionamento → triagem (botão/touch, texto e voz) → roteamento → chamado na central em tempo real, com modo discreto e confirmação. O foco é validar funcionalidades, não a robustez física.

Decisões desta fase: sem TPU (triagem roda no servidor com Ollama), sem gabinete (montagem aberta para apresentação), emissão só via API HTTP. Resiliência offline, TPU, multi-protocolo e central NOC completa ficam na projeção final.

02 — Escopo

Escopo — dentro e fora

Dentro (protótipo)

  • 1 totem: controlador + câmera + microfone + tela touch.
  • Triagem por botão/touch, texto e voz (STT).
  • Agentes (LangGraph + Ollama) no servidor.
  • Emissão via API HTTP + fila local (store-and-forward).
  • Central web: lista em tempo real, ACK, mudança de estado.
  • Modo discreto (trilha mulher).
  • Captura de vídeo (chamada e/ou evidência — ver §6).

Fora (vai para a projeção final)

  • Triagem offline em TPU (Hailo/Coral).
  • Gabinete antivandalismo, tamper, no-break.
  • Emissão MQTT / GSM / LoRa / sirene.
  • Central NOC com mapa de frota e relatórios PDF/CSV.
  • mTLS, RBAC completo e auditoria imutável.
  • Frota (vários totens) e atualização remota.

06 — Vídeo

Vídeo: bidirecional ou evidência

A meta é vídeo bidirecional (o atendente vê a pessoa durante o chamado). Mas isso depende de os destinos de triagem conseguirem receber esse vídeo — o que precisa ser validado antes de prometer o recurso.

Implementado: chamada WebRTC totem → central (sinalização SDP/ICE pelo backend em /rtc/{sala}, vídeo peer-to-peer) e registro de evidência local enviado a /evidencia ao encerrar. A integração de vídeo com WhatsApp/telefonia da CSV e da Sala Lilás permanece como incógnita a alinhar com cada unidade — por isso, fora da central, a câmera serve como evidência (gravação sob política), nunca como transmissão sem respaldo.

07 — Emissão

Emissão de alerta

No protótipo, o alerta usa o protocolo mínimo: POST /api/v1/eventos via HTTPS, com fila local (store-and-forward) garantindo que nada se perca em queda de rede. A confirmação ao usuário é dada pelo enfileiramento, não pela resposta do servidor.

Os demais caminhos entram como upgrade na projeção final, na ordem da escada de fallback:

  1. API HTTPS — implementado no protótipo.
  2. MQTT (broker + central em tempo real).
  3. GSM/4G — SMS + autodiscagem de voz (sem IP).
  4. LoRa/LoRaWAN — payload mínimo, longo alcance.
  5. Saída física — sirene/strobe ou alarme do campus.

Detalhes da escada completa na projeção final, §8.

10.2 Túnel HTTPS — Cloudflare Quick Tunnel (cloudflared)

A peça-chave que viabiliza a demonstração distribuída (totem na Raspberry Pi, servidor no notebook) sem necessidade de domínio próprio, certificado SSL ou configuração de firewall.

O que é

cloudflared tunnel --url http://localhost:5173 cria um túnel efêmero que expõe o frontend local (Bun, porta 5173) numa URL pública https://<slug>.trycloudflare.com. O script scripts/demo-tunel.sh automatiza: sobe o túnel, captura a URL, grava POTO_PUBLIC_BASE_URL no backend/.env e segura o processo em primeiro plano.

Por que é necessário

RequisitoProblema sem túnelComo o túnel resolve
HTTPS para câmera/microfoneNavegadores bloqueiam getUserMedia() em origens http:// fora de localhost. Sem câmera, não há WebRTC nem STT por voz.A URL https://…trycloudflare.com é um contexto seguro válido; o Chromium da Pi libera câmera e microfone sem flags especiais.
Origem única (API + WS + páginas)Sem o túnel, o totem na Pi precisa saber o IP do servidor para o backend (porta 8000) e outro para o frontend (porta 5173), com CORS aberto e WebSocket cruzando origens.O servidor Bun serve as páginas e faz reverse proxy de /api/* (HTTP e WebSocket) para o FastAPI. Uma URL serve tudo — sem CORS cross-origin e sem configuração de localStorage no cliente.
Webhooks de provedores externosO Twilio (ou qualquer callback HTTP) precisa alcançar o backend para postar statusCallback da ligação. Um localhost é invisível à internet.O túnel torna o backend acessível; POTO_PUBLIC_BASE_URL é usado pelo notifier para montar a URL de callback.
Acesso remoto para demonstraçãoApresentar o painel para um orientador ou banca exige que o sistema esteja acessível fora da LAN do desenvolvedor.Qualquer pessoa com a URL do túnel acessa o totem ou o painel — sem VPN, sem Tailscale no dispositivo do avaliador.

Implicações da decisão

  • URL efêmera: cada execução de cloudflared gera uma URL diferente. Se o túnel cair ou for reiniciado, o totem (e qualquer webhook configurado) precisa ser atualizado. Para uma demonstração controlada isso é aceitável; para operação contínua, não.
  • Dependência de internet: o túnel exige que o servidor (notebook) tenha acesso à internet. Em queda de rede externa, o totem na Pi ainda alcança o backend pela rede local (Tailscale ou LAN), mas perde HTTPS — e, portanto, perde acesso à câmera. A fila local (store-and-forward) garante que os chamados não se percam.
  • Latência adicional: o tráfego faz um "hairpin" (Pi → nuvem Cloudflare → volta ao notebook na mesma rede). Em LAN, a latência adicionada é de ~20–50 ms, imperceptível para a chamada WebRTC (que é P2P após a sinalização).
  • Dados em trânsito: o túnel Cloudflare descriptografa o TLS na borda e re-encaminha em HTTP para o localhost. Dados sensíveis passam pela infraestrutura da Cloudflare. Aceitável para protótipo; na operação final, a criptografia ponta-a-ponta exige infraestrutura própria.

10.3 Projeção futura — migração do túnel efêmero

O túnel efêmero é uma solução de prototipação. A evolução segue uma escada de maturidade:

FaseSoluçãoVantagemQuando
Atual (protótipo)Quick Tunnel (cloudflared --url)Zero configuração, zero custo, funciona em qualquer redeDemonstração e desenvolvimento
PilotoTúnel nomeado Cloudflare (cloudflared tunnel create poto) com subdomínio fixoURL estável (ex.: poto.seudominio.com); reconexão automática; pode rodar como serviço systemdTestes prolongados, validação com a CSV/Lilás
Produção campus (opção A)Reverse proxy institucional (Caddy/nginx) + certificado Let's Encrypt no domínio da UFPISem dependência externa; dados ficam na rede da UFPI; latência mínimaServidor alocado na UFPI com IP institucional
Produção campus (opção B)Tailscale com HTTPS (MagicDNS + certificados)Mesh VPN entre totens e servidor; HTTPS automático; zero firewall; funciona sem IP públicoSe a UFPI preferir não expor o serviço à internet pública

Decisão de arquitetura (ADR-009): o túnel efêmero é explicitamente temporário. Nenhuma funcionalidade do P.O.T.O depende do Cloudflare — apenas da presença de HTTPS. A migração para qualquer das opções acima é transparente: basta apontar o totem para a nova URL e atualizar POTO_PUBLIC_BASE_URL no .env.

10.4 Acesso alternativo sem túnel (Tailscale)

Para testes rápidos sem internet externa, o acesso direto via Tailscale (http://IP_TAILSCALE:5173) funciona para a API e o painel, mas não para a câmera/microfone (porque não há HTTPS). Para contornar temporariamente, inicie o Chromium na Pi com a flag:

DISPLAY=:0 chromium-browser \
  --unsafely-treat-insecure-origin-as-secure="http://IP_TAILSCALE:5173" \
  "http://IP_TAILSCALE:5173"

Esta flag é uma gambiarra de desenvolvimento e não deve ser usada em produção. Ela desativa proteções do navegador. O caminho correto é sempre HTTPS (via túnel ou certificado).
